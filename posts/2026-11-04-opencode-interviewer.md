# opencode これあると便利1選：曖昧な依頼を先に仕様にしてくれる interviewer

<!-- tags: opencode, 開発環境 -->

この記事は「opencodeこれあると便利1選 /interviewer みたいな感じで」という依頼から始まった。要するに「interviewer が便利だった話を書いて」としか言っていない。何を書くかは何も決まっていない状態だった。

そこで interviewer というスキルに頼んだ。依頼をそのまま実装に投げる前に、質問で仕様を固めて spec ファイルを書き出すやつ。この記事も、そこで作った spec に従って書いている。

## 何が起きたか

依頼を投げると、まず質問が返ってくる。`question` ツールで選択肢付きの質問が一度に4つ。1ラウンドで終わらず、4ラウンド・16問聞かれた。

最初のラウンドで聞かれたのはこういうこと。

> 「opencode これあると便利1選」はシリーズ名として扱う？ それとも今回の記事タイトルの一部？
>
> 読者は？ opencode を使っている人 / 聞いたことがある程度の人 / 未来の自分用メモ
>
> 記事の中心に置きたいのは？ 実際に使った体験 / 仕組みの説明 / 使いどころの判断

聞かれて初めて「シリーズにするつもりはないな」「読者は opencode を使っている人だな」と決まった。自分では言語化していなかっただけで、頭の中には答えがあった。それを引き出される感じ。

質問はテキストで垂れ流されるのではなく、必ず選択肢付きで返ってくる。答え終わると次のラウンド。4ラウンド目は「分量」「依頼文をそのまま載せるか」「末尾の一言」「ファイル名」まで聞かれた。ここまで来ると、書く前に決めることはほぼ残っていない。

## spec に残るもの

質問に答えると、spec ファイルが書き出される。日本語で書くルールになっている。後で自分が読み返して「これで合意した」と確認するためのものだから、書いた時と同じ言語でないと意味がない。

今回の spec の見出しはこうなった。

```
## 1. 目的
## 2. 位置づけ
## 3. 読者
## 4. タイトル
## 5. 構成案
## 6. 素材（事実として書いてよいこと）
## 7. 制約
## 8. ファイルと公開
```

「素材」の章が地味に効く。事実として書いていいこと（interviewer の動作、聞かれた回数、ファイルパス）が並んでいるので、記事を書くときに盛る余地がない。捏造しないブログにはちょうどいい。

interviewer はコードを一切変更しない。質問して spec を書いて終わり。実装はその後で普通に頼む。設計の前段だけを切り出したスキル、という理解でいい。

## 使ってみての不満

4ラウンドは長い。2ラウンド目あたりで「もう書けばいいのでは」と思った。答える側にもコストがかかるので、雑な依頼を投げたのに質問に16回答える羽目になる。

あと、選択肢がこちらより詳しいことがある。「そんな選択肢あるんだ」と新しい案を教えてもらうこともあったが、逆に「そこまで決めてなかった」ところまで決めさせられる。

小さな修正には明らかにオーバーキル。1行直すだけの依頼でこれをやると、質問に答える時間のほうが長くなる。

※ 16問答えたあとで「依頼文をそのまま載せるか」を聞かれて、そこは自分で決めろよと思った。
